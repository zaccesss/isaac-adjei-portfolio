01

NeoPixel LED Cube (4x4x4)

Arduino Uno C++ WS2812B KiCad PCB Design LDR Sensor
GitHub
Problem

I wanted to build something that combined hardware design, PCB layout, and firmware in one project. Most LED projects online are wired point-to-point and fall apart quickly. I wanted something properly engineered.

What I built

A 4x4x4 cube of 64 WS2812B LEDs on a custom PCB designed in KiCad. The firmware runs 5 animation modes using non-blocking millis() timing, so modes run smoothly without freezing the controller. An LDR sensor reads ambient light and adjusts brightness in real time.

Key decisions
  • Non-blocking animation loop using millis() instead of delay() for smooth multi-pattern switching
  • PROGMEM storage for animation data to keep RAM available for runtime logic
  • PCB trace width calculated for 5V / 500mA supply to prevent thermal issues
  • LDR calibrated against measured lux values for meaningful brightness response
What I learned

Power distribution matters more than I expected at this scale. I also learned how quickly a bad PCB layout can create noise that affects the timing of addressable LEDs. The full schematic-to-firmware process taught me to think in terms of the whole system, not just the code.

02

AstonCV

PHP 8.2 MySQL bcrypt CSRF PDO PDF Export
Live site
Problem

Students at my university had no standard place to store and share their CVs. Sending PDF files around by email is messy and doesn't version well. I wanted something functional, not just a course project.

What I built

A full-stack CV platform at astoncv.zacess.com. Users register, create their CV through a structured form, and export it as a formatted PDF. It runs on PHP 8.2 with MySQL, deployed on a VPS with Nginx.

Key decisions
  • 11 security layers: bcrypt password hashing, CSRF tokens, PDO prepared statements, input sanitisation, rate limiting, session security, and more
  • PDF generation handled server-side to avoid client-side library inconsistencies
  • Role-based access so users can only view and edit their own data
  • Deployed to a real VPS, not shared hosting, to get production experience
What I learned

Security cannot be an afterthought. I added authentication after the initial build and it cost me twice as long as building it in from the start would have. Building something live also taught me server configuration, Nginx, and debugging in production.

03

Two-Stage Audio Amplifier

TL071 Op-Amp OPA551 Proteus PCB Layout Oscilloscope
University project
Problem

Drive an 8-ohm speaker from a smartphone line-level output. The signal needs to be filtered, amplified to usable power levels, and the circuit needs to run from a single supply.

What I built

A two-stage amplifier: Stage 1 is a TL071-based active bandpass filter (9 Hz to 24.1 kHz). Stage 2 is an OPA551 power amplifier capable of delivering up to 0.56 W into 8 ohms. The circuit runs from a single +9 to 12 V supply using a virtual ground mid-rail.

Key decisions
  • Simulation in Proteus before building to validate component values and catch issues
  • Virtual ground biasing to run both op-amp stages from a single supply
  • PCB at 80mm x 50mm with reverse-polarity protection diode
  • Hardware results within plus or minus 0.5 dB of simulated response across the audio band
What I learned

Simulation and physical builds differ more than textbook examples suggest. Ground planes, component placement, and lead resistance all affect measured results. Getting within 0.5 dB of the simulated response required careful PCB layout.

04

CNC Milling Machine Control System

Arduino C++ Safety Logic LCD 16x2 State Machine
University project
Problem

CNC machines are safety-critical. The control system needed to prevent operation when the door is open, respond immediately to emergency stops, and give the operator real-time feedback throughout.

What I built

A microcontroller-based control system with a hardware and software door interlock, emergency stop with immediate motor cutoff, debounced multi-button input, and a 16x2 LCD display showing machine state in real time.

Key decisions
  • State machine architecture to make every possible transition explicit and testable
  • Hardware interlock as the primary safety mechanism, not software
  • Input debouncing handled in firmware to prevent phantom triggers
  • Alarm output on emergency stop that cannot be cleared without a reset sequence
What I learned

State machines are genuinely useful for safety-critical code. They force you to be explicit about what is allowed in each state, which makes edge cases visible before they become bugs. I also learned that fail-safe logic means defaulting to the safe state, not the convenient one.

05

Goods Lift Control System

Arduino C++ DC Motor Control LCD 16x2 Priority Queue
University project
Problem

Build a functional multi-floor lift controller. It needs to accept floor requests, travel to them in the right order, prevent over-travel, and respond correctly to safety conditions.

What I built

A microcontroller-based lift (elevator) system with multi-floor navigation, a priority-queue request handler, limit switches to prevent over-travel, real-time LCD floor and direction display, and door-open interlock logic.

Key decisions
  • Priority queue for floor requests, serving requests in travel direction before reversing
  • Limit switches as hardware-level safety, triggering hard stops independently of firmware
  • Emergency stop clears the queue and holds until manually reset
  • LCD updates on every state change, not on a timer, for accurate real-time feedback
What I learned

Queue-based scheduling is much cleaner than if-else chains for multi-stop navigation. I also learned that physical motor control introduces timing considerations that simulation does not capture well.
